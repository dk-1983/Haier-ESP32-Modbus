# Согласование MQTT-телеметрии, схема 1

Добавлено в v1.3.0. Результаты аппаратной проверки и проверки HA указаны в заметках к релизу. Идентификаторы climate, команды, регистры и GPIO сохранены. Код контроллера серверной этой правкой НЕ изменён.

## Зачем это сделано

MQTT Home Assistant может отфильтровывать одинаковые значения climate. Его last_reported не доказывает время последнего ответа кондиционера. Повторная публикация не должна омолаживать старое измерение или подтверждать команду.

## Передача

Топик `<prefix>/telemetry`, JSON, QoS 0, без retain. Публикация при подключении, после нового принятого статуса hOn (не чаще раза в 250 мс), либо каждые 5 секунд без нового кадра. Работает и во время ожидания подтверждения команды. Дополнительного опроса UART нет. Сообщения старше 250 мс в очереди рабочего потока отбрасываются; телеметрия не сохраняется как отложенная очередь QoS 0 при отключении. Задержку сети и брокера прошивка не ограничивает.

Обычный `<prefix>/state` сохраняет поведение, включая ожидание подтверждения. LWT availability сохранён. Discovery теперь создаёт восемь сущностей вместо пяти.

## Поля

Передаются существующие параметры состояния, включая available, mode, target_temperature, current_temperature, command_state, request_id, и дополнительные поля:

| Поле | Значение |
|---|---|
| schema | Целое 1; неизвестную схему не принимать. |
| boot_id | Случайный идентификатор запуска ESP: 32 шестнадцатеричных символа. Не серийный номер. |
| status_frames | Счётчик принятых UART-статусов; повторная публикация его не увеличивает. |
| age_ms | Возраст статуса при формировании JSON; null до первого статуса. |
| sample_uptime_ms | Монотонное время ESP в мс, 64 бита, при получении статуса; до первого статуса 0. |
| published_uptime_ms | Время формирования JSON на тех же часах. Не Unix-время, NTP не требуется. |
| fault_valid | Есть свежий статус, протокольная связь и полный блок датчиков. |
| fault | error_status != 0, либо null при недостоверных данных. |
| fault_code | Родной байт ошибки hOn 0..255, либо null. |

available=false при возрасте статуса от 30 секунд или недействительной протокольной связи. fault_valid дополнительно требует полного блока датчиков: короткий пакет не означает отсутствие ошибки. Расшифровка ненулевых кодов и соответствие кодам YCJ не заявляются. Ошибка оборудования, ошибка разбора UART и потеря связи — разные состояния.

## Новые сущности Discovery

- Telemetry: unique_id `<device_id>_telemetry`; значение — status_frames, полный JSON в атрибутах, force_update=true, диагностическая категория, expire_after=15 секунд.
- AC fault: unique_id `<device_id>_fault`; binary_sensor с классом problem, ON — ошибка. Атрибуты boot_id/status_frames/age_ms/fault_code. Требуются online брокера и fault_valid; expire_after=15 секунд.
- AC fault code: unique_id `<device_id>_fault_code`; числовой код, те же условия достоверности и истечение через 15 секунд.

Фактические entity_id назначает HA, пользователь может их менять. Находить по устройству/unique_id, не зашивать имя. Неизменный OFF у binary_sensor сам по себе не гарантирует обновления last_reported: использовать общий поток телеметрии.

## Задание для разработки контроллера серверной

Добавить необязательный выбор сущности телеметрии; прежнее поведение оставить для сторонних интеграций. Режим, уставку и ошибку читать из ОДНОГО снимка телеметрии, команды по-прежнему отправлять через climate. Температуры телеметрии всегда в °C, в отличие от атрибутов climate с системными единицами HA.

При реальном обновлении диагностической сущности проверять schema, типы, конечные неотрицательные времена, sample_uptime_ms <= published_uptime_ms, отсутствие restored, available и принадлежность нужному устройству. Запомнить монотонное время приёма в HA, сессию и идентификатор измерения. Обновлять этот кэш по событиям приёма, НЕ при каждом секундном чтении watchdog. После запуска дождаться живого обновления: восстановленные атрибуты не считаются новым пакетом. force_update диагностического сенсора позволяет получать события и при одинаковом значении.

Возраст источника = published_uptime_ms - sample_uptime_ms; затем прибавлять время после приёма. Это НИЖНЯЯ оценка реального возраста: задержка сети неизвестна. Можно добавить консервативный запас, но не выдавать его за гарантированную границу. Повторная отправка того же измерения не должна менять время его получения от кондиционера. Отбрасывать движение published_uptime_ms назад внутри сессии. Новый boot_id сбрасывает старую сессию и контекст подтверждения. Отдельно контролировать отсутствие сообщений 15 секунд и максимальный возраст источника 30 секунд, вместе с available/fault_valid.

Подтверждение команд нельзя заменять обновлением heartbeat или climate.last_reported. Сохранить требование измерения после команды. Топик result уже публикует accepted с идентификатором, сформированным прошивкой, затем confirmed/timeout_unconfirmed с тем же ID; телеметрия содержит request_id/command_state. confirmed означает два совпавших последующих ответа UART. Подписаться до отправки, сериализовать команды и сопоставлять accepted/result; другие интерфейсы тоже могут писать. Это НЕ новый протокол с идентификатором, заданным клиентом. Один рост счётчика не доказывает исполнение команды. Для строгой идентификации отправителя при конкурентных командах потребуется отдельное согласованное расширение протокола.

Значение по умолчанию ac_readback_timeout=3 секунды короче 30-секундного ожидания прошивки. Пересмотреть отдельно: 35 секунд — исходное предложение, не измеренная гарантия. Не путать с ac_max_age=180 и minimum_ac_off=180. Межблокировки вентиляции и компрессора сохранить.

Ошибка из того же снимка: достоверное false разрешает работу; true означает неисправность; недостоверность/пропуск означает unknown. Простое назначение нового binary_sensor без исправления проверки свежести вновь может дать ложный устаревший OFF.

## Проверки перед установкой

Программные проверки: Discovery, шаблоны, коды 0/1/255, недостоверная ошибка, интервалы и переполнение таймера, порог 30 секунд. Требуется сборка ESP. Аппаратно и в HA ещё проверить: неизменные показания более 180 секунд, выполнение команды, потерю UART/MQTT, перезапуск ESP/HA, неполный пакет, восстановленные сообщения и невозможность подтвердить команду старым heartbeat. Ненулевую ошибку имитировать в тестах, не создавать неисправность рабочего кондиционера. Нулевой код на исправном приборе не проверяет все аварии.
